# Member 1 data-contract compliance review

**Assessment date:** 2026-10-10
**Evidence scope:** integrated requirements, Part 1 specification, Part 2 input contract, Part 3 data requirements, current Member 1 source/tests, and the synthetic handoff example.
**Interpretation:** statuses describe this checkout. A passing implementation contract does not imply real-data or model readiness.

## Contract and downstream impact

- The shared canonical event, label, valuation, and prediction columns are unchanged. `prediction_id` remains the account/cutoff ID, `prediction_run_id` remains the inference-job ID, the 7/14/30 fields remain cumulative-compatible storage, event `occurred_at`/`received_at`/`source_available_at` meanings are unchanged, and MRR remains integer source minor units with ISO currency.
- As-of read helpers now accept a distinct `ServicePrincipal` with exact tenant, source, purpose, and role grants. Existing `IntegrationPrincipal` reads are narrowed to their bound source. Account-specific reads also require an identity mapping from a granted source, preventing canonical customer-ID probing across sources in the same tenant. A source integration cannot ingest through the service-principal type. Member 2 should use the new service-token provisioning flow when combining authorized usage, billing, and subscription sources.
- The `reliability_reasons` field remains a string array, but accepted values are now predefined codes. Part 2's descriptive example must map `"Short personal usage history"` to `short_personal_usage_history`; consuming UI may translate codes to static display text. Explanation JSON shape is unchanged, but string leaves are limited to bounded categorical feature identifiers and enums. Numeric model contributions remain valid.
- Service-principal persistence additionally requires role `analyst` and the explicit `model_artifact_write` purpose, alongside `retention_inference` and the exact source grants. An integration may persist only for customers mapped through its own source. Existing feature/label/prediction fields and IDs do not change.
- Migration 002 adds the scoped service-principal registry and stable subscription-owner table/composite FKs. Existing version-1 subscription records are preserved when ownership is consistent; initialization returns `contract_conflict` before applying migration 002 if legacy records claim one subscription for multiple customers. Migration 003 adds per-integration event-category grants and backfills only categories evidenced in existing canonical events; an unused legacy integration gets `usage` only. A trusted local operator must grant previously unobserved categories explicitly. No Member 2 labels/features or Member 3 decision logic were changed.
- Historical eligibility now treats availability-filtered subscription event history as authoritative because `customers.account_status` has no effective timestamp. Account-level closure/suspension semantics are unsupported until a dated source-backed lifecycle event is agreed.
