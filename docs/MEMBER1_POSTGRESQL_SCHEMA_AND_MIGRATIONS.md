# Member 1 PostgreSQL schema and migrations — Prompt 06C

Prompt 06C defines a PostgreSQL schema equivalent to the current SQLite
Data Foundation schema and a checksum-protected migration runner. It does not
port repository queries or establish Data Foundation behavior parity. The
SQLite migrations remain the authoritative SQLite initialization path.

## Schema source and translation rules

The schema below was derived by applying `migrations/001_data_foundation.sql`
through `migrations/004_dataset_identity_and_observation_coverage.sql` to an
in-memory SQLite database, then inspecting `sqlite_master`, `PRAGMA
table_info`, `PRAGMA foreign_key_list`, and `PRAGMA index_list` for the result.
That produced 18 application tables and six explicit query indexes.

| SQLite type / behavior | PostgreSQL representation | Reason |
|---|---|---|
| `TEXT` identifiers and text fields | `TEXT` | Preserves identifier and contract values. |
| `TEXT` columns ending in `_at`, plus `as_of`, `covered_from`, `covered_through` | `TIMESTAMPTZ` | Stores instants as timezone-aware PostgreSQL values. The 06D-1 ingestion path binds normalized ISO-8601 values as aware datetimes and formats integration-health timestamps back to the existing string contract; remaining query adapters are later work. |
| JSON serialized into SQLite `TEXT` | `TEXT` | Keeps the canonical serialized representation available to existing payload hashing and equality rules; PostgreSQL `JSONB` formatting must not become an input to the application hash. |
| SQLite `INTEGER` | `BIGINT` | Retains signed 64-bit integer range, including integer minor-unit amounts. `canonical_events.event_id` is `BIGINT GENERATED BY DEFAULT AS IDENTITY`. |
| SQLite `REAL` | `DOUBLE PRECISION` | Matches the current floating probability and coverage-completeness fields. |
| Composite tenant keys and foreign keys | PostgreSQL composite PK/UNIQUE/FK constraints | Retains tenant-aware referential integrity in the database. |
| SQLite `ON DELETE CASCADE` | PostgreSQL `ON DELETE CASCADE` | Preserves the current ownership cleanup behavior. Prediction-to-feature-snapshot reference remains non-cascading, matching SQLite. |

Timestamp storage changes representation: PostgreSQL normalizes instants and
drivers return timezone-aware `datetime` values, while SQLite stores the
original normalized ISO-8601 text. The source occurrence time and optional
source-availability time remain separate columns. No policy for occurrence,
receipt, or availability cutoffs changes here.

values, category grants, dataset identity, and import checkpoints.

## Migration layout and runner

PostgreSQL-specific SQL is in `migrations/postgresql/`, with versions aligned
to SQLite's logical milestones:

| PostgreSQL migration | Schema contribution |
|---|---|
| `001_data_foundation.sql` | Tenant, identity, event, subscription, feature, label, and prediction tables plus base indexes. |
| `002_authorized_services_and_subscription_owners.sql` | Service principals, subscription ownership registry, and ownership FKs. |
| `003_integration_event_categories.sql` | Explicit category grants and legacy-safe backfill. |
| `004_dataset_identity_and_observation_coverage.sql` | Dataset identity, observation coverage, and resumable import checkpoints. |
| `005_rls_and_least_privilege.sql` | Locally tested capability-role grants, tenant RLS, global-table restrictions, and trusted-backend token authentication lookup. See the separate 07B-1 security acceptance document. |
| `006_artifact_authorization_scope.sql` | Source-scoped authorization reads needed for real artifact persistence under the artifact-writer capability; no source-event reads. |
| `007_restore_global_maintenance_grants.sql` | Forward correction restoring only maintenance grants on global dataset/checkpoint tables that migration 005's final revoke removed. |

`retaniq.postgresql_migrations` validates strict, contiguous `NNN_name.sql`
versions, reads UTF-8 files, and computes SHA-256 over the exact file bytes.
The `retaniq_schema_migrations` table records version, checksum, and applied
time. A changed applied file, unknown recorded version, missing applied file,
or non-prefix history stops initialization without attempting repair.

The runner takes a session-level PostgreSQL advisory lock for the selected
schema. It uses one transaction per migration and writes that migration's
checksum row in the same transaction as its DDL. A failed migration rolls back
both its DDL and history row; completed earlier migrations remain recorded.
The lock is released in `finally` and also by closing the connection after a
process failure. Repeated initialization verifies checksums and applies no
already-recorded migrations. DDL runs only when the operator explicitly runs
`python -m retaniq init-db --db <target>` or calls
`initialize_database(target, migrate_postgresql=True)`.

For a local TLS-disabled test server, the CLI additionally requires
`--allow-insecure-local-postgresql`. This option cannot relax the remote TLS
requirement and must not be used for a production connection.

The optional `schema` argument to `run_postgresql_migrations` is restricted to
a simple identifier and exists for isolated local test schemas. The default is
`public`. The runner creates that schema when requested and sets `search_path`
for its session. It does not drop or recreate tables, migrate SQLite data, or
repair a manually altered schema.

To inspect applied versions and checksums after connecting to the selected
database/schema, query:

```sql
SELECT version, checksum, applied_at
FROM retaniq_schema_migrations
ORDER BY version;
```

## Local verification setup

The optional driver is installed from `requirements-postgresql.txt` into an
isolated local Python environment. SQLite mode remains dependency-free.

PostgreSQL integration tests only enable when all of these are true:

- `RETAINIQ_POSTGRES_TEST_DISPOSABLE=1` is explicitly set;
- `RETAINIQ_POSTGRES_TEST_DSN` is present;
- the DSN host is loopback (`localhost`, `127.0.0.1`, or `::1`); and
- the database name begins with `retaniq_test_`.

Tests create a uniquely named schema within that database and remove only that
schema afterward. They never accept an arbitrary remote DSN. Do not use a
production or Supabase credential. For a local test-only cluster, a DSN can
use `sslmode=disable`; that setting requires the explicit local test opt-in in
the test harness or the `init-db` CLI flag and is not acceptable for remote
targets.

Run:

```powershell
python -B -m unittest discover -s tests -p 'test_postgresql_migrations.py' -v
python -B -m unittest discover -s tests -v
python -B -m compileall -q retaniq tests
git diff --check
```

Without the guarded local test environment, PostgreSQL integration tests are
reported as skipped with the guard reason. Unit tests still cover ordered
discovery, duplicate and invalid versions, contiguous history, checksum
validation, statement splitting, target rejection, explicit initialization,
and redacted failures. A skipped PostgreSQL test is not evidence of a real
connection or schema verification.

## Current limitations and remaining work

This is schema implementation, not `POSTGRESQL_FEATURE_PARITY`. Prompt 06D-1
now provides bounded PostgreSQL ingestion, identity, authentication,
authorization, subtype persistence, and import-checkpoint operations; other
Data Foundation repository operations continue to reject PostgreSQL. The
existing SQLite queries use `?` placeholders, SQLite row/index access,
`INSERT OR IGNORE`, `BEGIN IMMEDIATE`, text timestamps, and SQLite-specific
exception handling. Prompt 06D-2 must add reviewed historical-query and
coverage compatibility while preserving temporal availability, MRR currency
rules, dataset checks, and all current SQLite tests.

At the 06C milestone this schema had no RLS policies; application
authorization was not considered a replacement for database-enforced row
security. Prompt 07B-1 now adds migrations 005–007 and a role bootstrap. Its
partially verified local status, trust boundary, migrations 005–007, and
remaining limitations are documented in
[the 07B-1 security acceptance](MEMBER1_POSTGRESQL_RLS_AND_AUTHORIZATION.md).
No Supabase database is initialized by this runner, and no production-ready
claim is made.

## Evidence status

PostgreSQL 16.15 schema verification passed on a temporary local cluster and
test-only database. The guarded integration suite applied versions 001–004,
checked all expected table/column/type/nullability entries and constraint
catalogs, exercised tenant foreign keys and uniqueness, round-tripped
timezone-aware timestamps, JSON text, and integer minor units, verified
probability constraints, checked failed-migration rollback and checksum
rejection, repeated initialization, and serialized concurrent migration
attempts. `SELECT 1` and the explicit `init-db` initialization path also passed.
The temporary cluster and test database were removed after verification. This
supports `POSTGRESQL_SCHEMA_VERIFIED_ON_DISPOSABLE_INSTANCE`; it does not
support feature parity or production readiness. No SQLite database contents
were copied to PostgreSQL.
